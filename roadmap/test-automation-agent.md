## P2 — integrations (~q3-4)
- [ ] [P2] [decomposed] CI integrations (GitHub Actions/Jenkins) result ingestion — researched 2026-09-09: GitHub needs a GitHub App (checks:write scope — plain OAuth apps/PATs can't create check runs) that POSTs to /repos/{owner}/{repo}/check-runs on push/PR and updates it to completed+conclusion when the SpecPilot run finishes (docs.github.com "Building CI checks with a GitHub App"). Jenkins side: the Outbound Webhook plugin (NOT Generic Webhook Trigger, which triggers INTO Jenkins, the wrong direction) sends build-event payloads OUT to an external endpoint. Decomposes into: (1) a generic `POST /api/ci/webhook` ingestion endpoint accepting {provider, repo, commit_sha, status, run_id}, (2) a GitHub-specific outbound path using the Checks API to report SpecPilot's own run status back onto the PR, (3) a docs page with copy-paste GitHub Actions YAML + Jenkins plugin config. {cat: backend; size: M; research: web; sources: docs.github.com/en/free-pro-team@latest/developers/apps/creating-ci-tests-with-the-checks-api, plugins.jenkins.io/outbound-webhook}
- [ ] [P2] [decomposed] Knowledge-base / test-selection helpers {cat: backend; size: M; multifile: no; research: repo}
- [ ] [P2] [decomposed] Flake-state Slack/webhook alerts — When a test's rolling flake ratio crosses a configured threshold (or a previously-stable test starts failing intermittently), push a message to a Slack/Discord/generic webhook URL configured per-project, and post a follow-up when it stabilizes. This reuses the flake-ratio computation and CI ingestion events already planned (GitHub Checks/Jenkins webhook) as the trigger source — no new data source, just a notification sink off existing state transitions. Stays test-run scoped because it fires on flake-ratio state changes only, not generic error/log alerting; it's the single highest-leverage feature for getting a first team to check the tool daily instead of only visiting the dashboard. {cat: backend+web; size: S; multifile: yes; research: none — completed 2026-09-10, sources: Trunk Flaky Tests Slack integration (trunk.io/flaky-tests), BuildPulse per-repo flake notifications (docs.buildpulse.io)}
- [ ] [P2] [decomposed] "Fix-first" ranking view — Add a dashboard view/API endpoint that ranks tests by (flake-rate × run-frequency) so a team can see which handful of flaky tests are costing the most CI time/trust, rather than an undifferentiated flaky-tests list. Pure derived-data feature computed entirely from run records and flake ratios already ingested via the CI integrations; no new collection surface. Stays scoped to test-run triage (a prioritized to-do list for existing flake data) rather than sliding into general analytics/observability. {cat: backend+web; size: S; multifile: yes; research: none — completed 2026-09-10, sources: CircleCI Test Insights "most failed/flakiest tests" ranking (circleci.com/docs/guides/insights/insights-tests), Buildkite Test Analytics slowest/least-reliable dashboard}
- [ ] [P2] [decomposed] Per-test flake-rate trend chart — On each test's detail page, render a time-series/sparkline of its flake ratio and pass/fail history over recent runs (last N days or last N runs), so a team can see whether a test is getting better, worse, or newly-flaky at a glance instead of only a point-in-time ratio. Requires storing/aggregating flake ratio per run-window rather than just a rolling scalar, but the underlying run records already come from the planned CI ingestion pipeline — this is a read-model/charting addition, not a new data source. Stays in scope as a visualization of test-run pass/fail history, not logs or infra metrics. {cat: backend+web; size: M; multifile: yes; research: none — completed 2026-09-10, sources: Buildkite Test Analytics historical/graph trend views (buildkite.com/resources/blog/fixing-flaky-tests), Datadog Flaky Test Management history-across-runs (docs.datadoghq.com/tests/flaky_management)}
- [ ] [P3] [decomposed] PR-comment run summary — Post a single upserted PR comment (via the same GitHub App/token used for the planned Checks API integration) summarizing the run: pass/fail counts, which tests are newly flaky, and a link to the run's dashboard page — distinct from the Checks API status badge, since a comment is scannable in the PR conversation without opening a details link. Reuses the existing GitHub integration's auth and webhook events; only adds a comment-upsert call keyed on PR number. Stays scoped to summarizing this repo's test-run results, not general CI/build commentary. {cat: backend; size: S; multifile: no; research: none — completed 2026-09-10, sources: BuildPulse PR comments/blocking on new flakes (buildpulse.io/products/flaky-tests), general flaky-test PR-comment pattern across CircleCI/Buildkite integrations}
