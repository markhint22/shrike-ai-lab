# Roadmap — shrike-monitor (uptime + heartbeat brick)
**Maturity:** MEDIUM (monitors/results/incidents exist). **Stopping point:** a COMPLETE, dogfooded v1 that replaces the ad-hoc deploy_watch scripts. INFRASTRUCTURE — reach v1 and freeze.

- [ ] [P1] [decomposed] Monitor create validation + ping-token-shown-once security {cat: backend; size: S; multifile: no; research: repo}
- [ ] [P1] [blocked-ops] Dogfood: replace the fleet's deploy_watch/deploy_health scripts with real monitors {cat: infra; size: M; research: web} -- RESEARCHED 2026-09-09 (Claude): the CODE side is already done (MonitorScheduler actively polls http monitors on interval, checker.py + heartbeat dead-man logic + notifier.py already publishes status transitions to a shrike-notify topic). Nothing left to decompose into a fleet backlog item -- nothing in shrike-monitor's OWN repo needs writing. What remains is pure ops/integration, out of the fleet's per-repo-code-edit model: (1) shrike-monitor isn't deployed anywhere live yet -- deploy it (Railway backend, same pattern as the other 7 apps); (2) register the real production health-check URLs from deploy_watch.sh's SURFACES list as monitors via POST /monitors; (3) decide whether to retire deploy_watch.sh's ad-hoc `hc()` polling in favor of reading GET /monitors/status, or keep deploy_watch.sh for what shrike-monitor CANNOT do (Railway/Vercel deploy-status + auto-enqueue-a-fix, which needs the Railway/Vercel CLIs, not just an HTTP health check). Tagged blocked-ops (not needs-research/ready) so the planner stops re-surfacing this as a fleet gap -- it is a deployment decision for a human/Claude session, not code the 27B can write.
## P2 — light surface (only if needed)
- [ ] [P2] [decomposed] Minimal status page/API for the fleet dashboard to read {cat: backend; size: S; multifile: no; research: repo}
- [ ] [P2] [decomposed] Seed scheduler status baseline from persisted results on restart — currently MonitorScheduler._last_status/_incident_state start empty every process start (app/services/scheduler.py), and rehydrate() (app/store.py) only restores monitors/results, not scheduler state; the first tick after a restart always treats each monitor's status as a fresh baseline (old_status is None) and skips notify, so a monitor that goes down or recovers during shrike-monitor's own restart window silently misses its transition alert. - [ ] [P2] [decomposed] Wire downtime duration into notifier alert bodies — app/utils/duration.py's humanize_seconds() is fully implemented and unit-tested (backend/tests/test_utils.py) but never imported by app/services/notifier.py; a down transition alert currently says only changed from up to down with no indication of how long the prior state lasted. - [ ] [P2] [decomposed] Heartbeat monitors never record down/up CheckResults, leaving uptime_ratio and incident history blind — app/routers/heartbeat.py's ping() only ever records CheckResult(ok=True); a missed heartbeat is detected live in MonitorScheduler.tick()/_maybe_notify() (app/services/scheduler.py) via heartbeat_status(), but no CheckResult(ok=False) is ever stored, so uptime_ratio() (app/models.py) and GET /monitors/{id}/incidents (app/routers/monitors.py, which also hard-returns [] for non-http types) both report near-100% uptime and zero incidents for a heartbeat monitor that has been down for hours. Have MonitorScheduler record a synthetic CheckResult on each heartbeat status transition (down/up) so uptime_ratio and incident history reflect real downtime, plus regression tests in backend/tests/test_scheduler.py and backend/tests/test_heartbeat.py. {cat: backend; size: M; multifile: yes; research: none}
- [ ] [P2] [decomposed] Notifier retries hammer shrike-notify with no backoff — app/services/notifier.py's notify_transition() loops up to max_retries+1 times with zero delay between attempts (no asyncio.sleep, no jitter), so a shrike-notify outage gets every retry fired in the same instant instead of spaced out; app/utils/jitter.py's with_jitter() is fully implemented and unit-tested (backend/tests/test_utils.py) but never imported anywhere in app/. Add an awaited backoff delay (base delay scaled by with_jitter()) between retry attempts in notify_transition, with tests in backend/tests/test_notifier.py asserting backoff behavior via a fake/injected sleep. {cat: backend; size: S; multifile: yes; research: none}
- [ ] [P2] [decomposed] GET /health never checks whether MonitorScheduler's background loop is alive — app/main.py's health() returns a static Health(status="ok") regardless of whether scheduler._task has died (e.g. crashed and never restarted); this is exactly the "silent failure" class of bug shrike-monitor exists to catch in other services, applied to itself. Expose a liveness signal (e.g. MonitorScheduler.is_running() checking self._task.done()/cancelled, plus a last-tick timestamp) and surface it on GET /health (extend app/schemas.py's Health) so a dead scheduler shows up as unhealthy instead of masquerading as ok, with tests in backend/tests/test_scheduler.py and an extended health test. {cat: backend; size: S; multifile: yes; research: none}
