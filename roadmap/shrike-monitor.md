Nothing left to decompose into a fleet backlog item -- nothing in shrike-monitor's OWN repo needs writing. What remains is pure ops/integration, out of the fleet's per-repo-code-edit model: (1) shrike-monitor isn't deployed anywhere live yet -- deploy it (Railway backend, same pattern as the other 7 apps); (2) register the real production health-check URLs from deploy_watch.sh's SURFACES list as monitors via POST /monitors; (3) decide whether to retire deploy_watch.sh's ad-hoc `hc()` polling in favor of reading GET /monitors/status, or keep deploy_watch.sh for what shrike-monitor CANNOT do (Railway/Vercel deploy-status + auto-enqueue-a-fix, which needs the Railway/Vercel CLIs, not just an HTTP health check). Tagged blocked-ops (not needs-research/ready) so the planner stops re-surfacing this as a fleet gap -- it is a deployment decision for a human/Claude session, not code the 27B can write.
## P2 — light surface (only if needed)
- [ ] [P2] [decomposed] Minimal status page/API for the fleet dashboard to read {cat: backend; size: S; multifile: no; research: repo}
- [ ] [P2] [decomposed] Seed scheduler status baseline from persisted results on restart — currently MonitorScheduler._last_status/_incident_state start empty every process start (app/services/scheduler.py), and rehydrate() (app/store.py) only restores monitors/results, not scheduler state; the first tick after a restart always treats each monitor's status as a fresh baseline (old_status is None) and skips notify, so a monitor that goes down or recovers during shrike-monitor's own restart window silently misses its transition alert. Seed _last_status (computed via overall_status/heartbeat_status against rehydrated results) in app/main.py's lifespan or MonitorScheduler.start() before the first tick, plus a regression test in backend/tests/test_scheduler.py. {cat: backend; size: S; multifile: yes; research: none}
- [ ] [P2] [decomposed] Wire downtime duration into notifier alert bodies — app/utils/duration.py's humanize_seconds() is fully implemented and unit-tested (backend/tests/test_utils.py) but never imported by app/services/notifier.py; a down transition alert currently says only changed from up to down with no indication of how long the prior state lasted. Compute elapsed time since the last transition in MonitorScheduler._maybe_notify (app/services/scheduler.py) and pass it through Notifier.notify_transition (app/services/notifier.py) to include a humanized duration in the alert body/title, with tests added to backend/tests/test_notifier.py and backend/tests/test_scheduler.py. {cat: backend; size: S; multifile: yes; research: none}
## Stopping point (HARD)
Once monitors + heartbeats + incidents work and the fleet dogfoods it: **v1 COMPLETE — freeze.** No PagerDuty-scale features. It's a dead-man's-switch + uptime brick.
