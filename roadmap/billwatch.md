# Roadmap — BillWatch
**Maturity:** HIGH (live, web+iOS+Android). **Wedge:** simpler/cheaper *federal-only* consumer tracker vs FastDemocracy. **Stopping point:** federal tracking + digests + alerts + AI summaries, mobile at parity → maintain; don't chase 50-state coverage.

## P1 — the consumer wedge (next ~2 quarters)
- [ ] [P1] [decomposed] Weekly digest (grouped by stage/topic) + endpoint + view {cat: backend+web; size: M; multifile: yes; research: repo}
- [ ] [P1] [decomposed] Real-time alerts on tracked topics/bills (rules + match) {cat: backend+web; size: M; multifile: yes; research: repo}
- [ ] [P1] [decomposed] Plain-English "what changed" status summaries {cat: backend; size: S; multifile: no; research: repo}
## P2 — mobile parity + polish (~q3-4)
- [ ] [P2] [decomposed] iOS/Android feature parity with web (tracking, digests, alerts) — researched 2026-09-09: both apps are NATIVE (Swift/SwiftUI iOS, Kotlin Android — not Flutter/cross-platform as earlier notes assumed). They've already DIVERGED from EACH OTHER, not just from web: iOS has AICoachingView/AdvancedAnalyticsView/CareerHistoryTimelineView/LegislatorFinanceView/RecommendationsView that Android lacks; Android has BillTrackingScreen/AdvancedFilterScreen/PaywallScreen/TopicsScreen that iOS lacks. This is a 3-way gap (mobile-vs-mobile as much as mobile-vs-web), not a simple "port web to mobile." First real task: audit each of the ~30 backend routers + ~19 web views against what each native app actually consumes, then close mobile-vs-mobile gaps first (cheaper, both apps already have the muscle memory) before mobile-vs-web. {cat: mobile; size: L; research: web}
- [ ] [P2] [decomposed] Legislator profiles + scorecards surface polish {cat: web; size: M; multifile: yes; research: repo}
- [ ] [P2] [decomposed] Committee hearing & floor-activity calendar for tracked bills — Surface a "This Week in Congress" view showing scheduled committee hearings/markups for bills a user follows, pulled from Congress.gov's documented `/committee-meeting` endpoint (filterable by chamber/date range, already the same data source BillWatch's `committee_sync_service` and `committees` router consume). Fits the wedge: federal-only, single unified calendar (not 50-state schedules), and it's a natural next hop from committee data already synced rather than new infrastructure. Ties directly into existing alert/digest plumbing (a hearing becomes another alert-worthy "what changed" event). {cat: backend+web; size: M; multifile: yes; research: none — completed 2026-09-10, sources: github.com/LibraryOfCongress/api.congress.gov CommitteeMeetingEndpoint.md, congress.gov/help/committee-schedule-meetings-hearings}
- [ ] [P2] [decomposed] Shareable bill status cards — One-tap "share" on any tracked bill generates a branded image/link card (bill number, plain-English status line, latest vote tally, BillWatch logo) for text/social, reusing the existing plain-English status-summary text (`status_change_summary.py`) and vote data (`models/vote.py`) already in the DB — no new data source, just an OG-image/render endpoint plus a share button in the 3 clients. Fits the wedge as a near-zero-cost, high-leverage growth loop for a solo dev (free user acquisition vs. FastDemocracy's sales-led enterprise motion) without adding any tracking scope beyond federal bills already followed. {cat: backend+web; size: S; multifile: yes; research: none — completed 2026-09-10, sources: FastDemocracy.com feature review (G2/SourceForge), GovTrack.us feature survey}

- [ ] [P3] [decomposed] Plain-English bill "odds of passage" indicator — A lightweight, transparent heuristic (not ML) scoring a bill's chance of advancing, based on stage, days-since-introduction, committee, and historical base rates computed from BillWatch's own synced bill-history data (`bill_sync_service`, `bill_stage.py`), presented as a plain-language line ("similar bills at this stage became law ~12% of the time") consistent with BillWatch's existing "what changed" plain-English framing.
