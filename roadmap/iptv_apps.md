# Roadmap — Chickadee / iptv_apps
**Maturity:** HIGH (~95% — live, multi-platform). **Stopping point:** once DVR+VOD+multistream ship and it's in both app stores, it's feature-complete → maintenance + content-ops only. Don't chase Fubo's channel count.

## P1 — competitive parity + store launch (next ~2 quarters)
- [ ] [P1] [decomposed] Cloud DVR — record/list/delete, retention policy, RecordingsView — every rival has it {cat: backend+web; size: L; multifile: yes; research: repo}
- [ ] [P1] [decomposed] VOD / on-demand catalog + tab — Sling Freestream angle {cat: backend+web; size: M; multifile: yes; research: repo}
- [ ] [P1] [decomposed] Multiple simultaneous streams (plan-based limit + 409 guard) {cat: backend; size: S; multifile: no; research: repo}
- [ ] [P1] [decomposed] App Store + Play Store submission blockers — RevenueCat is already SDK-wired for iOS/Android with API keys and product IDs configured, but Apple Guideline 3.1.1 and Google Play's subscription policy both mandate native in-app purchase (not Stripe) for any digital subscription bought inside the app, so remaining IAP work is finishing App Store Connect/Play Console product setup plus sandbox testing, not new integration. The bigger blocker is content rights: Chickadee's Xtream/M3U playlist-import architecture is exactly the pattern Apple's 5.2.2/5.2.3 guidelines target, and reviewers will require documentary proof — a signed licensing contract or authorization letter from each channel/content rights-holder — attached in App Review Information, or rejection is near-certain. That proof-of-rights posture is a business call Shrike Labs must make (license specific channels vs. reposition as a bring-your-own-already-licensed-playlist player with matching ToS/UI), and can't be resolved by coding alone. Sequencing: finish RevenueCat/IAP store-side config and sandbox tests now (buildable), settle the content-rights/licensing decision next, then submit with the authorization documentation attached last. {cat: infra; size: M; multifile: yes; research: none — completed 2026-09-10, sources: developer.apple.com/app-store/review/guidelines (3.1.1/5.2.2/5.2.3), support.google.com/googleplay/android-developer/answer/10281818}
- [ ] [P1] [decomposed] YouTube support follow-through — an MVP already exists (curated news/government/space/local channels as a free-content Discover source, Sling-Freestream-style differentiation: backend CuratedYouTubeChannel model + youtube_channel_checker.py quota-aware Data API v3 poller + youtube_channel_job.py APScheduler 30min job + GET /api/discover/youtube, tested via test_youtube_channel_checker.py + test_discover_youtube_endpoint.py; web DiscoverView.vue YouTube tab; iOS YouTubeChannelPlayerView.swift; Android YoutubePlayerActivity.kt) — this item is the remaining gaps: (1) `GET /api/discover/youtube` has NO auth/premium-tier gate — every other stream source goes through app/services/premium.py's is_premium/get_stream_limit, this one bypasses it entirely, decide + implement the gate; (2) it's architecturally siloed from the core Stream model (app/models/__init__.py) used by every other source — decide whether that's fine long-term (curated-only, never mixed with user-added M3U/Xtream sources) or whether it should unify; (3) Android has an UNCOMMITTED local fix for the WebView black-screen bug (two confirmed root causes via live DevTools instrumentation: the embedded WebView's " wv" User-Agent token makes YouTube serve a degraded/blackened player, AND a CSS 0-height layout race from percentage-height chaining before the WebView is measured — fixed by stripping " wv" from the UA and switching to position:fixed + viewport units) sitting in YoutubePlayerActivity.kt — needs a build/lint verification pass (no Android build tooling available in this session to verify), removal of the leftover `WebView.setWebContentsDebuggingEnabled(true)` temp-debug line, and this repo has ZERO Android instrumented tests for this file — add some; (4) no admin/editorial flow exists to add/curate channels — only via hand-written Alembic migrations; (5) no tvOS YouTube playback found; (6) add E2E coverage (Playwright/Appium/XCUITest) for the Discover YouTube tab — none exists; (7) silent-warning-only startup check for a missing YOUTUBE_API_KEY should probably hard-fail or alert instead. {cat: backend+web+mobile; size: M; multifile: yes; research: repo}

## P3 — differentiation (~year 2)
- [ ] [P3] [decomposed] Profiles + parental controls depth; kids mode — Chickadee already has `Profile`/`ParentalSettings`/rating-hierarchy models, enforcement services, and a `ProfilesView.vue` UI, so scope this as finishing PIN-gated profile switching end-to-end and wiring `kid_max_rating`/`blocked_categories` into stream+discover queries on web/iOS/Android, plus a simplified kids-mode UI (bigger tiles, filtered grid) rather than a separate app — mirroring Plex's preset restriction-profile+PIN-unlock model and Sling's 2026 Minor's Profile (grid-level rating filter, no bespoke content-review team). Avoid building a custom rating taxonomy or per-title manual review queue — reuse the existing TV-Y…TV-MA/G…NC-17 hierarchy already in `parental.py`. {cat: backend+web; size: M; multifile: yes; research: none — completed 2026-09-10, sources: Plex Support - Parental Controls (support.plex.tv), Sling TV parental controls guide (thestreamable.com)}
- [ ] [P3] [decomposed] Personalized discover/recommendations — Chickadee's `StreamDiscoveryService` already exposes `/personalized`, `/similar`, `/genre`, `/trending` endpoints and a `ForYouRow.vue` component, so scope this as tuning/finishing that existing heuristic engine (genre-tag matching via `Content.genres`/`Stream.category`, recency/region-based trending, continue-watching-adjacent suggestions) and fully surfacing it in `DiscoverView.vue`, not building a new ML pipeline. This matches how small catalogs get value from content-based/metadata filtering plus light curation (e.g. HBO Max's human-curated + algorithm hybrid) rather than collaborative-filtering ML, which would be disproportionate infra/maintenance for Chickadee's catalog size — explicitly avoid adding a model-training pipeline. {cat: backend+web; size: M; multifile: yes; research: none — completed 2026-09-10, sources: Content-based Recommendation Engine for Video Streaming (arxiv.org/pdf/2308.08406), AI-Based Personalisation in Streaming Platforms (miquido.com)}
## Stopping point
When P1+P2 ship and stores accept it: FEATURE-COMPLETE. After that, only content/EPG ops, bug-fixes, and OS-version upkeep. Do NOT add live-TV-provider-scale features.
